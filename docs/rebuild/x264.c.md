# x264.c — rebuild specification

## 1. Header

- Source path: `x264.c` (root of the reference tree).
- Role: the command-line front end: option parsing, input/output module selection, frame pipeline, progress/status reporting, signal handling and top-level lifecycle.
- Marker: **dirty-side behavioural specification** — full behaviour and structure in our own words.

## 2. Purpose

`x264.c` is the executable that users actually run. It bridges the shell and libx264: it interprets roughly two hundred option spellings, discovers the source format and destination container, wraps the demuxer in a video-filter chain, assigns timestamps, drives the encoder call by call, writes the resulting NALs through a muxer, and finally prints statistics. It must reproduce precisely the CLI's ordering rules (presets before user options, fast-first-pass before profile, profile before opening), because those rules determine the resulting bitstream. It also implements the Windows-specific UTF-8 command-line and console-title handling, and the Ctrl-C graceful-abort path.

## 4. State and data structures

- `cli_opt_t` — the CLI's run-state bundle:
  - `b_progress` — progress indicator enabled (default 1).
  - `i_seek` — first frame to encode.
  - `hin`, `hout` — opaque input/output handles.
  - `qpfile`, `tcfile_out` — open file streams for forced frame types and timecode output.
  - `timebase_convert_multiplier` — factor applied to input PTS when the user supplies a different timebase.
  - `i_pulldown` — selected pulldown mode index.
- Globals: `cli_input` (selected demuxer op-table), `cli_output` (selected muxer op-table), `filter` (head of the video-filter chain), `cli_log_level` (starts at `X264_LOG_INFO`), `b_ctrl_c` (volatile Ctrl-C flag), and on Windows `org_console_title`.
- String tables: AVC-Intra classes `50,100,200,300,480`; CQM presets `flat,jvt`; log levels `none,error,warning,info,debug`; partitions `p8x8,p4x4,b8x8,i8x8,i4x4,none,all`; pulldown `none,22,32,64,double,triple,euro`; range `auto,tv,pc`; output CSPs filtered by build (i400/i420/i422/i444/rgb); valid profiles filtered by build; demuxers `auto,raw,y4m` plus conditional avs/lavf/ffms; muxers `auto,raw,mkv,flv` plus conditional mp4.
- `cli_pulldown_t` — a pulldown descriptor: repeat modulus, an array of up to 24 `pic_struct` values, and an FPS multiplier factor. The table defines: 2:2 (mod 1, one top-bottom pattern, factor 1.0); 3:2 (mod 4, four field patterns, factor 1.25); 6:4 (mod 2, double/triple, factor 1.0); double (mod 1, factor 2.0); triple (mod 1, factor 3.0); euro/pulldown 24 (mod 24, 24 patterns, factor 25/24).
- `pulldown_frame_duration[10]` — duration in frame units indexed by `pic_struct`: 0.0 for auto, 1 for progressive/top-bottom/bottom-top, 1.5 for the three-field variants, 2 for double, 3 for triple.
- `enum OptionsOPT` — enum values in the 256+ range for the CLI-handled long options, keeping them distinct from single-character short options.
- `QP_MAX_SPEC = 51 + 6*2 = 63`, `QP_MAX = 63 + 18 = 81` — the accepted ranges for forced QP and CRF lower bound display.

## 5. Algorithm / behaviour

### 5.1 `main` lifecycle

1. If `argc == 4` and `argv[1] == "--autocomplete"`, call the completion entry point immediately and return; no threading/encoder initialization occurs.
2. Initialize threading support; fail with `unable to initialize threading` on error.
3. On Windows: retrieve the command line as UTF-8 and rebuild `argv`; save the original console title; switch stdin/stdout/stderr to binary mode.
4. Call `x264_param_default`, then `parse`. A parse failure sets `ret = -1`.
5. Restore the console title (input modules may change it), register the SIGINT handler, and call `encode` only if parsing succeeded.
6. Cleanup in a fixed order: release the input through the filter chain's `free` hook when present, otherwise through `cli_input.close_file`; close the output; close the timecode and qpfile streams; call `x264_param_cleanup`; on Windows restore the title again and free the rebuilt argv.
7. Return `ret`.

### 5.2 Help and version output

`help` has three tiers: basic (`-h`) always prints the header block, syntax, examples, profile/preset/tune names, frame-type and rate-control headings and the I/O basics; `--longhelp` adds most analysis, threading and logging options; `--fullhelp` adds every option plus profile/preset/tune descriptions, VUI details, CQM matrices and filter help. `print_version_info` prints the point version (or a fallback `0.<build>.X`), versions of compiled-in external libraries, build date, compiler name/version, CLI and library chroma-format configurations, and the license line; with swscale it also prints the library license and warns when the binary is unredistributable. The CSP listing wraps names at 80 columns using a 32-character indent and a `, ` separator, and includes libavformat pixel-format names when available.

### 5.3 Two-pass parse

The parser deliberately runs `getopt_long` twice:

- **Pass one** only records `--preset` and `--tune` and fails on an unknown option (`?`). If the preset is `placebo`, `b_turbo` is cleared. If either string was given, `x264_param_default_preset` is invoked; otherwise plain defaults remain.
- **Pass two** performs the real parse. A fresh `defaults` structure is filled for help text and to seed `cli_log_level`. Input/output option structures are zeroed; input bit depth starts at 8; input/output range starts at `RANGE_AUTO`; progress starts enabled; output CSP starts from defaults.

Special CLI-side cases in pass two set flags or store values locally rather than calling the API parser:

- Frames/seek clamp negatives to zero; output/muxer/demuxer/index/tcfile/timebase/pulldown/video-filter/input-format/resolution/colorspace/depth/output-CSP/input-range/range/profile/stats-output are recorded in local variables or directed into `cli_input_opt_t`/`cli_output_opt_t` structures.
- `--quiet` sets both CLI and encoder log level to `NONE`; `-v` sets both to `DEBUG`; `--log-level` accepts a name from the log-level table (offset by `X264_LOG_NONE`) or a numeric value.
- `-r`, `--fps` and any interlaced option set `b_user_ref`, `b_user_fps`, `b_user_interlaced` before falling through to the generic parser. `--fps` additionally forces `b_vfr_input = 0`.
- Output CSP values are parsed from the CLI name list then translated into the library CSP constants via a fixed index map whose length depends on `X264_CHROMA_FORMAT`.
- `--input-range` and `--range` shift the parsed enum by `RANGE_AUTO` so `0` means limited and `1` means full.
- All other options are forwarded to `x264_param_parse` with the long-option name and `optarg`, letting the API handle numeric conversion, boolean inversion for `no-*` spellings and underscore normalization. A nonzero return produces `x264 [error]: invalid argument: <name> = <value>` and aborts.

After pass two, when `b_turbo` is set, `x264_param_apply_fastfirstpass` is called; then `x264_param_apply_profile` with the requested profile (or `NULL`). Missing input or output produces `No input file` / `No output file` with a pointer to `--help`.

### 5.4 Output selection

`select_output` chooses a muxer by explicit `--muxer` value (unless `auto`) or by filename extension, treating `-` as raw. MP4 (when compiled with GPAC or L-SMASH), Matroska and FLV all switch the encoder to length-prefixed NALs (`b_annexb = 0`) and suppress repeated headers (`b_repeat_headers = 0`). MP4 additionally downgrades CBR NAL-HRD to VBR with a warning because CBR HRD is incompatible with that container. Anything else selects the raw Annex-B muxer.

### 5.5 Input selection and stream information

`select_input` computes an extension from the filename for auto mode; standard input is treated as raw. Regular-file detection gates the Avisynth and FFmpeg Source probes. Module resolution order: explicit `avs`, `d2v`, `dga` extensions or `avs` demuxer map to Avisynth; `y4m` maps to the YUV4MPEG driver; `raw` or `.yuv` maps to the raw driver; otherwise the code tries FFmpeg Source, libavformat and Avisynth (when compiled) in that order, then raw as a last resort. Failure to obtain any handle yields `could not open input file ... via any method!`.

The `video_info_t` handed to the demuxer is seeded from user parameters (CSP, fps, full-range flag, interlacing, SAR, field order, VFR). After opening, SAR and fps fractions are reduced and the line `<width>x<height><p|i> <sar-w>:<sar-h> @ <fps-num>/<fps-den> fps (<c|v>fr)` is logged at info level. Width/height must be positive and at most `MAX_RESOLUTION` (16384).

A timecode file replaces the input clock; combining it with `--fps` is rejected. `--timebase` is rejected for CFR input. Threaded input is inserted when the source advertises thread safety and either `--thread-input` is set, threads exceed one, or threads are automatic on a multi-core machine; the depth-specific wrapper (`thread_8_input`/`thread_10_input`) is chosen by `i_bitdepth`.

### 5.6 Timebase, user overrides and filter chain

User-specified SAR and fps overwrite detected values; CFR sources get a timebase of `fps_den/fps_num`. A `--timebase` string may be `num/den` or a single denominator (numerator inherited); values above `UINT32_MAX` are rejected. A conversion multiplier is computed from the user and detected timebases and applied to each PTS later. User interlacing overrides detected interlacing. If input range was forced, it overwrites the detected full-range flag.

`init_vid_filters` registers the built-in filters and builds the chain: a `source` filter wrapping the demuxer, a `resize` filter in normalization mode, and a `fix_vfr_pts` filter, followed by the user's slash-separated filter sequence (each token optionally carrying `:option=value`). Resolution is taken from the demuxer when not forced by the user. Output CSP is adjusted only when the requested format is "narrower" than or different from the source: I400 forces monochrome; I420 is forced when source is below I420 or at I422+; I422 when source is outside the I422–I443 band; I444 when outside I444–BGR; RGB when in the packed-RGB band. The high-depth flag is preserved. Unforced full-range inherits the source. A final `resize` and a depth filter (`bit_depth=N`) complete the chain.

After filtering, fps/timebase/SAR are copied back into the encoder parameters. Frame count is reduced by `i_seek` and capped by `--frames`. If the source looks interlaced and the user did not override, interlaced mode is enabled with a warning naming the detected field order (or a warning that the build lacks interlaced support). RGB sources default to full range and reject limited range. Finally, if the user did not explicitly set `--ref`, the reference count is reduced until `mbps * refs` fits the chosen level's DPB limit.

### 5.7 QP file handling

`parse_qpfile` is called per output frame index (including `i_seek`). It scans lines of the form `<frame> <type> [qp]`, skipping entries earlier than the current frame and seeking back to the byte offset of an entry beyond it. Type letters map `I`→IDR, `i`→I, `K`→keyframe (IDR or I depending on open-GOP), `P`→P, `B`→BREF, `b`→B; any other letter invalidates the line. QP must be `-1` or within `0..QP_MAX`; a valid non-negative QP is stored as `i_qpplus1 = qp+1`. Malformed lines are reported with `can't parse qpfile for frame %d`, and the qpfile is closed and disabled. If seeking back fails, `qpfile seeking failed` is reported.

### 5.8 Encode loop and output pipeline

Setup: pulldown is enabled only for CFR input; it sets `b_pulldown`/`b_pic_struct`, derives the timebase from fps and the pulldown factor, and rejects framerates where `fps * factor` is not integral. The encoder is opened, its normalized parameters are read back with `x264_encoder_parameters`, and passed to `cli_output.set_param`. Ticks per frame are computed as `timebase_den * fps_den / timebase_num / fps_num`, forced to at least one for CFR. When headers are not repeated, SPS/PPS/SEI are written once through `cli_output.write_headers`. A timecode-v2 file begins with `# timecode format v2`.

Per frame:

1. Exit when Ctrl-C is set or the frame limit is reached.
2. Pull a `cli_pic_t` through `filter.get_frame`; end of input breaks. Initialize the library picture, then copy strides, plane pointers, plane count, colorspace and PTS into it.
3. In CFR mode PTS is simply the frame index. With pulldown, `pic_struct` comes from the pattern modulo and PTS accumulates the per-struct duration (rounded to nearest integer with `+0.5`). Otherwise, if a timebase multiplier exists, PTS is scaled and rounded.
4. Non-monotonic PTS (`pts <= largest_pts`) triggers a warning naming frame and values, up to three warnings (`MAX_PTS_WARNING`), then a single "suppressing further warnings" message; PTS is forced to `largest_pts + ticks_per_frame`. Debug level disables the cap.
5. Timecode output writes PTS converted to milliseconds with six decimals. The qpfile may override frame type and QP.
6. `encode_frame` calls `x264_encoder_encode`; on success and nonzero size it hands `nal[0].p_payload` plus the total byte count to `cli_output.write_frame` and records `pic_out.i_dts`. Negative returns abort the loop with error status; zero output (delay) is normal.
7. `filter.release_frame` returns the frame to the source. Progress is refreshed at most every `UPDATE_INTERVAL` microseconds.

After the input loop, delayed frames are flushed with `NULL` input until `x264_encoder_delayed_frames` reports zero, using the same output path. Duration is derived from PTS/DTS with special cases: a single output frame uses one frame time; Ctrl-C uses `2*last_dts - prev_dts - first_dts`; normal termination uses `2*largest_pts - second_largest_pts`, scaled by the timebase. The progress line is erased, the encoder closed, and an abort line printed when Ctrl-C was seen. The output is closed with the largest and second-largest PTS, and a final summary `encoded N frames, F fps, B kb/s` is printed when at least one frame was emitted.

### 5.9 Logging format

`x264_cli_log` suppresses messages whose level exceeds `cli_log_level`, maps levels to the lowercase words `error`, `warning`, `info`, `debug` (anything else to `unknown`), and writes `<name> [<level>]: ` to stderr followed by the formatted message using the library's `x264_vfprintf` (which understands x264-specific `%` extensions). `x264_cli_printf` writes the message without a prefix. The progress line intentionally strips the leading `x264 ` prefix by printing from offset five, appends two spaces and a carriage return, sets the full string as the console title, and flushes stderr. The final summary uses plain `fprintf` and therefore is not subject to the log-level gate.

### 5.10 Signal handling

A file-static volatile integer `b_ctrl_c` is set by a one-line SIGINT handler registered after parsing. The encode and flush loops test it before every iteration. Because the flush loop is also gated on it, Ctrl-C skips draining delayed frames; the encoder is still closed and outputs finalized. The abort message reports both `opt->i_seek + i_frame` (input frame) and `i_frame_output`. Cleanup then proceeds normally in `main`.

### 5.12 Speed-relevant CLI options

Highest impact: `--preset` (and `--tune fastdecode`/`zerolatency`), `--me` (dia → hex → umh → esa → tesa), `--subme` (0–11), `--ref`, `--partitions`, `--trellis`, `--b-adapt`, `--rc-lookahead`, `--aq-mode`, `--no-mbtree`, `--no-psy`, `--nr`, `--8x8dct`, `--weightp`, `--fast-pskip`, `--dct-decimate`, `--pass 1` (turbo) with `--slow-firstpass` as the opt-out. Threading knobs `--threads`, `--lookahead-threads`, `--sliced-threads`, `--sync-lookahead`, `--non-deterministic` trade throughput, latency and repeatability. `--asm`/`--no-asm`, `--cpu-independent` and `--opencl` select kernel implementations. `--frames` and `--seek` bound work directly. `--no-progress`, `--psnr`/`--ssim` and `--dump-yuv` have small but real costs. VFR input and pulldown add timestamp processing.

## 8. Performance notes

The CLI's own per-frame work is small relative to encoding, but several choices matter:

- Progress printing is throttled to one update per 250 ms; removing the throttle or printing to a slow terminal would measurably hurt high-fps encodes. Console-title updates happen on the same path.
- `print_status` computes fps and bitrate with doubles and formats one line; this is negligible at standard frame rates but is the only per-frame formatting work.
- The qpfile scanner keeps its file position and seeks back when a future frame is encountered, avoiding a full re-read per frame; frequent random access patterns can still cost I/O.
- Threaded input exists specifically to overlap demuxing with encoding; enabling `--thread-input` (or automatic threading) can prevent the demuxer from becoming the bottleneck on many-core systems.
- The filter chain is built once; per-frame it only pulls/pushes through function pointers. Keeping the chain minimal (no unnecessary resize/depth filters) avoids copies.
- VFR/pulldown paths do extra timestamp arithmetic; CFR with `--fps` is the cheapest.
- Encoding speed is dominated by the option mapping in section 5.12. For fastest output: a fast preset, `--me dia`, low `--subme`, `--ref 1`, no trellis/8x8dct/mbtree, sliced threads for low latency, and `--frames` to bound work. For best quality per bit: `placebo`, `--me tesa`, `--subme 11`, high refs, all partitions and trellis 2.
- Reproducible benchmarks should use `--threads 1`, fixed preset, `--no-progress`, and identical input; the encoder's non-deterministic optimizations are disabled by default but CPU-dependent algorithm selection is not unless `--cpu-independent` is set.
- Public references: x264 preset and tuning guide (project wiki), `doc/threads.txt` (threading latency/throughput trade-offs), `doc/ratecontrol.txt` (two-pass and VBV behaviour), `doc/vui.txt` (timestamp/VUI semantics), and the x264 API documentation in `x264.h` for option meanings.

## 10. Verification checklist

- `x264 --version` prints a point version, compiler and license lines; `x264 --help`, `--longhelp`, `--fullhelp` produce increasing amounts of text.
- An unknown long option prints `x264 [error]: invalid argument: ...` and exits negative; a missing input or output prints the corresponding `No ... file` message.
- `x264 --preset placebo` skips fast-first-pass while `x264 --pass 1` applies it; `--slow-firstpass` suppresses the turbo settings.
- Output extension selection: `.264` → raw Annex-B with start codes and repeated SPS/PPS; `.mkv`/`.flv`/`.mp4` → length-prefixed NALs without repeated headers; MP4 + CBR HRD downgrades to VBR with a warning.
- Input auto-detection: `.y4m` is read as YUV4MPEG; a raw `.yuv` file with `--input-res`/`--input-csp` is accepted; stdin defaults to raw; unsupported files produce `could not open input file ... via any method!`.
- The source-info log line reports the correct dimensions, SAR, fps and `cfr`/`vfr` marker; dimensions above 16384 are rejected.
- `--fps` with `--tcfile-in` is rejected; `--timebase` with CFR input is rejected.
- `--frames 10 --seek 5` encodes ten frames starting from frame five.
- A qpfile with `I`, `i`, `K`, `P`, `B`, `b` entries produces the expected frame types and QPs; a malformed line disables the qpfile with the documented error.
- CFR output has PTS equal to frame indices; a deliberately nonmonotonic timecode file triggers at most three warnings plus a suppression note, and PTS are forced forward.
- `--pulldown 32` on 29.97 fps produces the expected `pic_struct` sequence and a 1.25× timebase factor; unsupported framerates are rejected.
- Ctrl-C during encoding stops the loop, skips flushing, prints `aborted at input frame X, output frame Y`, and still closes output and prints final stats.
- Final line format `encoded N frames, F fps, B kb/s` matches the observed output size and elapsed time.
- `--quiet` suppresses tagged logs but not the final summary; `-v` enables per-frame debug logs and disables the progress cap; `--no-progress` removes the carriage-return status line.
- `--psnr`/`--ssim` produce per-frame metrics and `--dump-yuv` writes reconstructed frames.
