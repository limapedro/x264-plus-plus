# `common/aarch64/mc-c.c` — AArch64 motion-compensation dispatcher

> Dirty-side behavioural specification (reverse-engineered from the reference encoder; describes behaviour, not code).

## 1. Header

- Source path: `common/aarch64/mc-c.c`
- Role: declares all AArch64 MC kernel prototypes, builds the function-pointer tables (weight tables, copy/avg tables), implements the C-level `mc_luma`/`get_ref` helpers, and wires the accelerated kernels into `x264_mc_functions_t` according to CPU features.
- This is a **dirty-side behavioural specification** artifact for the clean-room reimplementation.

## 2. Purpose

The generic motion-compensation layer calls through a table of function pointers. This file is the AArch64 side of that contract: it decides which NEON/SVE implementation fills each slot, provides the small C glue that selects half-pixel reference planes and applies weights, and caches the best weight-kernel variant for each `x264_weight_t`.

## 3. Public interface

Exported functions:
- `void x264_mc_init_aarch64( uint32_t cpu, x264_mc_functions_t *pf );` — populates the function table.

Declared (and assigned) kernel symbols include the full set documented in `mc-a.S.md` and `mc-a-sve.S.md`, plus the macro-generated wrappers `mbtree_propagate_list_neon` (from `PROPAGATE_LIST`), `plane_copy_neon`, `plane_copy_swap_neon`, `plane_copy_interleave_neon` (from `PLANE_COPY`/`PLANE_COPY_SWAP`/`PLANE_INTERLEAVE` macros defined in common headers).

Internal static tables:
- `pixel_avg_wtab_neon[6]`: `{NULL, w4, w8, w16, w16, w20}` — index is `width >> 2`; width 12 reuses w16 because it is not slower.
- `mc_copy_wtab_neon[5]`: `{NULL, w4, w8, NULL, w16}` — no 12-wide copy.
- `mc_wtab_neon`, `mc_nodenom_wtab_neon`, `mc_offsetadd_wtab_neon`, `mc_offsetsub_wtab_neon`: generated by `MC_WEIGHT()` for the four weight variants, each indexed by `width >> 2` with the same w4/w8/w16/w20 pattern.

Internal static functions:
- `weight_cache_neon( x264_t *h, x264_weight_t *w )`
- `mc_luma_neon( dst, dst_stride, src[4], src_stride, mvx, mvy, width, height, weight )`
- `get_ref_neon( dst, *dst_stride, src[4], src_stride, mvx, mvy, width, height, weight )`

## 4. State and data structures

- `x264_mc_functions_t pf`: the destination table; fields assigned include prefetch functions, `avg[]`, `copy[]`, `weight`, `offsetadd`, `offsetsub`, `weight_cache`, `mc_chroma`, `mc_luma`, `get_ref`, integral initializers, lowres init, chroma load/store, plane copies, and hpel filter.
- `x264_weight_t w`: fields `i_scale`, `i_denom`, `i_offset`, `weightfn[]`, `cachea[]`.
- `src[4]`: four half-pixel reference planes (integer, horizontal, vertical, centre).
- `x264_hpel_ref0[]` / `x264_hpel_ref1[]`: common lookup tables mapping the quarter-pixel index to the two reference planes needed for interpolation.

## 5. Algorithm / behaviour

### `weight_cache_neon`

Selects the cheapest weight kernel and caches the offset:
1. If `i_scale == 1 << i_denom` (unity scale): choose `mc_offsetsub_wtab_neon` when `i_offset < 0` and store `−i_offset` in `cachea[0]`; otherwise choose `mc_offsetadd_wtab_neon` and store `i_offset`.
2. Else if `i_denom == 0`: choose `mc_nodenom_wtab_neon` (multiply-add without shift).
3. Else: choose the full `mc_wtab_neon` (multiply, shift by denominator, add offset).

### `mc_luma_neon`

1. Compute `qpel_idx = ((mvy & 3) << 2) + (mvx & 3)` and the integer offset `= (mvy >> 2)*stride + (mvx >> 2)`.
2. Select `src1 = src[x264_hpel_ref0[qpel_idx]] + offset`; if `(mvy & 3) == 3`, add one extra stride row (the reference table deliberately points one row early for the 3/4 case).
3. If `qpel_idx & 5` is nonzero (quarter-pixel interpolation needed): select a second plane `src2 = src[x264_hpel_ref1[qpel_idx]] + offset + ((mvx & 3) == 3)`, call `pixel_avg_wtab_neon[i_width >> 2]` to average the two planes, then optionally apply the cached weight function in place.
4. Else if a weight function exists: apply it from `src1` to `dst`.
5. Else: copy using `mc_copy_wtab_neon[i_width >> 2]`.

### `get_ref_neon`

Same selection logic as `mc_luma_neon`, but when no interpolation and no weight are needed it returns `src1` directly and sets `*i_dst_stride = i_src_stride` (zero-copy fast path). Otherwise it writes into `dst` and returns `dst`.

### `x264_mc_init_aarch64`

Assignments proceed in feature tiers:
1. `X264_CPU_ARMV8`: prefetch functions (no SIMD required).
2. `X264_CPU_NEON`: MB-tree, memory utilities, all `avg[]` block sizes, copy functions, weight tables and cache, chroma interpolation, `mc_luma`, `get_ref`, integral initializers, lowres init, chroma load/store, plane copies, hpel filter.
3. In 8-bit builds with `HAVE_SVE` and `X264_CPU_SVE`: override the four 4-wide `avg[]` entries with the SVE kernels. This override happens **after** the NEON assignments, so SVE wins where available.

Note: no SVE2 overrides exist in this dispatcher.

## 7. Constants and tables

- `PIXEL_4x2` … `PIXEL_16x16` enum indices used for `avg[]`/`copy[]`.
- `X264_CPU_ARMV8`, `X264_CPU_NEON`, `X264_CPU_SVE` feature flags.
- Weight-structure offsets 32 (denominator), 36 (scale), 40 (offset) used by the assembly; the C code reads/writes the same fields symbolically.
- `1 << i_denom` unity-scale test.

## 8. Performance notes

Initialization runs once; dispatch decisions are made per block through the function pointers and the `qpel_idx` computation (a few integer ops). The zero-copy `get_ref` fast path is important for integer-pel motion vectors without weighting.

Optimization tip for a clean-room port: keep the same tiered override structure so the selected kernel is deterministic for a given CPU mask; this matters for bitstream reproducibility. SVE tip: only 4-wide averaging is overridden in the reference; extending SVE to other widths must preserve rounding/saturation exactly. Public references: x264 function-table architecture; ARM CPU feature detection documentation.

## 10. Verification checklist

- For each CPU feature combination, verify the assigned function pointers match the documented tiers.
- `weight_cache_neon` selects the expected kernel for unity/no-denom/full-weight cases with positive and negative offsets.
- `mc_luma_neon` matches a scalar half-pixel interpolator for every `mvx&3`, `mvy&3` combination (16 cases), with and without weights.
- `get_ref_neon` returns `src1` and updates stride only on the zero-copy path.
- Table indices never exceed array bounds for supported block widths (4, 8, 16, 20 → indices 1, 2, 4, 5).
