# `tools/checkasm-arm.S` — dirty-side behavioural specification

## 1. Header

- Source path: `tools/checkasm-arm.S`.
- Role: the 32-bit ARM assembly support layer for the conformance tool: two variants (with and without NEON register checking) of a callee-saved-register trampoline with argument relocation and stack alignment handling.
- Marker: this file is a **dirty-side behavioural specification**; the mechanisms are described in our own words.

## 2. Purpose

AAPCS on 32-bit ARM requires r4–r11 (and, when NEON is in use, q4–q7) to survive a call. This file generates two wrappers that poison those registers, call a kernel through an indirect branch, and verify the values afterwards. A separate "noneon" variant is needed because not every kernel or build uses NEON, and pushing q4–q7 unnecessarily would be costly and could disturb non-NEON code.

## 3. Public interface

| Symbol | Signature / role |
| --- | --- |
| `x264_checkasm_call_neon` | `intptr_t (intptr_t (*func)(), int *ok, ...)`. ABI checker including q4–q7 verification. |
| `x264_checkasm_call_noneon` | Same signature, without NEON register checking. |

Both are generated by a single macro parameterised by a variant name. The C tool selects the NEON variant when NEON is detected at run time; otherwise it uses the noneon variant. The include of the shared ARM macro header provides `function`, `const`, `movrel` and `EXT`.

## 4. State and data structures

- `register_init`: an aligned table of eight 64-bit constants. The first four are compared against q4–q7 in the NEON variant; all eight are compared against r4–r11 in both variants.
- `error_message`: NUL-terminated failure text.
- `MAX_ARGS` is 15.
- `ARG_STACK` is `4*(MAX_ARGS-4)` = 44 bytes — the space needed for the eleven arguments beyond the four passed in registers.
- `ARG_STACK_A` rounds that reservation up so total stack use remains 8-byte aligned, taking already-pushed words into account.
- `pushed` tracks the number of bytes pushed, including 16 words for q4–q7 in the NEON variant.
- No mutable global state.

## 5. Algorithm / behaviour

### 5.1 Wrapper generation

For each variant:

1. Push r4–r11 and the link register. In the NEON variant also push q4–q7 and increase the pushed-byte count accordingly.
2. Use `movrel` to point a scratch register at `register_init`; load q4–q7 (NEON variant only) and r4–r11 from it, consuming the table sequentially.
3. Push the `ok` pointer on the stack.
4. Reserve the aligned argument area.
5. For each argument from the fifth onward, read it from the caller's frame at an offset beyond the saved registers and store it into the new argument area.
6. Move the function pointer into a scratch register, move the third and fourth incoming arguments into r0 and r1, and load the fifth and sixth from the argument area into r2 and r3 with a doubleword load.
7. Call the kernel with `blx`, release the argument area and pop the `ok` pointer into r2.
8. Push the kernel's return registers r0/r1 aside, reset the source pointer to `register_init`, and check registers:
   - NEON variant: load q0–q3 from the constant table, XOR each against q4–q7, OR the four results together, fold the 64-bit lanes with a vector OR and a reverse-halfword operation, and extract a 32-bit result.
   - Noneon variant: initialise the accumulator to zero.
9. For each GPR pair r4/r5, r6/r7, r10/r11, load the expected constants, XOR and OR into the accumulator. On non-macOS systems r8/r9 are also checked; on macOS r9 is volatile in the iOS ABI, so only r8 is checked.
10. Compare the accumulator to zero. If nonzero, store zero through the `ok` pointer, obtain the failure message with `movrel`, call `puts` via `blx`, and then restore the return registers, NEON registers (if applicable), r4–r11 and the link register.
11. Return to the caller through the restored link register.

### 5.2 Alignment handling

`ARG_STACK_A` is computed so that the total amount pushed is a multiple of eight, preserving the stack alignment expected by AAPCS. The source explicitly documents this purpose. The wrapper reads caller arguments using a computed offset that includes the saved registers, the pushed NEON registers and the `ok` slot.

## 8. Performance notes

- The NEON wrapper pushes and pops sixteen words of q-registers per call, making it substantially heavier than the noneon variant. Conformance use only; benchmark samples bypass it.
- Register checks use vector XOR/OR chains rather than scalar loops, keeping the verification path short.
- Stack alignment is maintained by rounding the argument reservation, which also avoids unaligned doubleword loads on kernels that require them.
- Extensibility tip: if a future ARM ABI marks another register callee-saved, add it to both the poison load list and the check macro, and update the `pushed` accounting.

### 8.1 Using checkasm-style verification to accelerate faster kernels

For 32-bit ARM kernel development:

- Select the NEON wrapper when the kernel uses q4–q7 as scratch; the noneon wrapper will not detect those mistakes.
- The r9 exception matters on macOS/iOS targets: a kernel that legitimately uses r9 there will not be flagged, but the same kernel on other ABIs will be. Test both when shipping both.
- The 64-bit-return alias used by the C tool means functions such as variance must verify return values through a direct call, not through this trampoline; keep that in mind when adding a new 64-bit-returning kernel.
- Use the benchmark mode after conformance passes, and remember that the gas preprocessor may translate this file differently on each assembler target.

## 10. Verification checklist

- Both wrappers return the kernel's result when registers are preserved.
- Clobbering any checked GPR causes `ok` to be zeroed and the failure message printed.
- In the NEON variant, clobbering any of q4–q7 causes failure.
- In the noneon variant, NEON registers are not checked.
- r9 is checked on non-macOS builds and skipped on macOS builds.
- The first four arguments arrive in r0–r3 before the call; later arguments arrive in order from the relocated stack area.
- Total stack usage is a multiple of eight in both variants.
- Saved registers and link register are restored exactly on both success and failure paths.
