# I0 — box-structure verification argument

Status: **increment I0, implementation side**. All claims below are review
arguments derived from `spec/cli-blackbox.md`, `docs/rebuild/x264cli.h.md`,
`docs/rebuild/input/input.h.md`, `docs/rebuild/input/input.c.md`,

No reference source was read; no oracle was run; no functional test was run.
The only execution performed was the compile/link check recorded in §6.

## 1. Black box → state box → clear box

### 1.1 Black box (required external behaviour)

```
CLI0( args, input_bytes ) -> ( stderr_log, stdout_text, exit_code, output_bytes )
```

For I0 the `output_bytes` component is **always empty**: the codec core is an
honest stub. The observable contract therefore reduces to:

* help/version requests produce stdout text and exit 0;
* malformed/usage-invalid invocations produce the specified stderr diagnostic
  and exit −1;
* a structurally valid invocation opens the input, reports its properties,
  then reports `x264 [error]: codec core not yet certified` and exits −1
  without creating an output file.

### 1.2 State box

```
( stimulus, old_state ) -> ( response, new_state )
```

`old_state` is process state: the active log level, the parsed option events,
the last preset/tune names, the first positional filename, and the byte-source
position inside the input file. The refinement keeps this state explicit in:

* `cli_state_t` and `option_events_t` (`src/cli/cli.c`) — all CLI-visible state;
* `x264pp_input_t` / `byte_source_t` (`src/cli/input.c`) — stream position,
  push-back buffer, next frame index, reusable frame buffer;
* `x264pp_output_t` (`src/cli/output.c`) — chosen muxer and output stream;
* `x264pp_param_t` (`src/core/api.h`) — the resolved parameter block passed
  across the API boundary.

Nothing in the input module depends on encoder internals, and the encoder stub
never touches input/output state. This separation is what lets I1..I5 replace
the core without changing the CLI.

### 1.3 Clear box (procedural decomposition)

```
main
  -> x264pp_cli_main
       -> parse_args -> find_long_option / find_short_option -> handle_cli_option
       -> [help/version exit]
       -> finalize_params
            -> param_defaults -> apply_preset -> apply_tune(s) -> apply_option*
       -> presence checks (output, input)
       -> x264pp_input_open
            -> io_read / io_unread (probe)
            -> open_raw | open_y4m
       -> timebase compatibility check
       -> print_input_info -> x264pp_log
       -> x264pp_encoder_open  [STUB: terminates here in I0]
       -> x264pp_output_open -> input loop -> x264pp_encoder_encode
          -> x264pp_output_write -> close chain
```

## 2. Per-function verification arguments

Each argument is an *intended function* claim: assuming the callees behave as
specified, the function produces exactly the box response above.

| Function / section | Intended function and why the refinement preserves the box above |
| --- | --- |
| `main` | Calls exactly one entry point and returns its status unchanged, so the OS-visible exit code is the CLI's exit code (−1 for every failure). |
| `x264pp_log` | Formats `<component> [level]: <message>\n` on stderr and suppresses levels above the active one. The four level names and the component tag are the spec's log format; using stderr for every diagnostic preserves the stdout/stderr split. |
| `find_long_option`, `find_short_option` | Total lookup over a null-terminated table: each documented long name and short alias resolves to one id, and an absent name yields NULL. Therefore no documented option is silently misrouted and every unknown name is rejected. |
| `parse_args` | One left-to-right pass over argv. `--` switches all remaining words to positional; the first positional word becomes the input and later ones are ignored; options after a positional word are still parsed (E3). Long options are split at the first `=`, so both `--name value` and `--name=value` resolve identically (E1). Missing arguments and unknown names are rejected with the documented getopt-style text. Because the loop does not stop at the input filename, E2 is possible. |
| `handle_cli_option` | Splits immediate CLI controls (output, input-related strings, help flags, log level, preset/tune names) from deferred encoder parameters. Keeping the *last* preset/tune name and recording other parameters as events is what makes explicit options win regardless of command-line order (E2). |
| `events_add`, `events_clean` | Appends a value copy for each explicit option and releases all copies exactly once. Since no event is applied during parsing, no early option can be overwritten by a later preset. |
| `param_defaults` | Establishes the documented default parameter block (section 5 of the spec) before any preset/tune/event is applied. Zero means the documented automatic behaviour (`threads`, `frames`, `keyint` for infinite, `min-keyint` for auto). |
| `apply_preset`, `apply_tune` | Each known name changes exactly the fields listed in spec sections 6.2/6.3; an unknown name emits the documented diagnostic. Applying a preset before a tune and both before events realises `defaults -> preset -> tune -> explicit`. A comma-separated tune is applied token by token. |
| `apply_option` | Maps every deferred option to one parameter mutation, using the spec's numeric parsing/clamping rules where they are documented and rejecting the explicitly invalid strings (`me`, `fps`, `sar`, `deblock`, profile, output csp). Out-of-range numeric values are clamped rather than rejected (E12). Options that belong to later increments are parsed and validated but have no bitstream effect; this is recorded rather than guessed. |
| `parse_int`, `parse_double`, `parse_ratio`, `clamp_*`, `gcd_u64` | Reject trailing junk (so `--fps bad` and `--crf abc` fail), accept rationals and floats for `--fps`, and reduce fractions with Euclid's identity. Clamping is silent, matching E12. |
| `x264pp_input_open` | Opens `-` as stdin and any other path as a file. In auto mode a file is probed for `YUV4MPEG2`; stdin is never probed (E9). A failed probe pushes the consumed bytes back so raw reading starts at byte 0. Explicit `--demuxer y4m` validates the magic and emits `y4m [error]: bad sequence header magic`. The two concrete readers then fill `x264pp_input_info_t` and own all allocated state. On any failure `*input` stays NULL and the module's detailed line has already been logged. |
| `open_raw` | Requires a resolution and emits exactly `raw [error]: raw input requires a resolution.` when it is absent (E7). Computes `W*H*3/2` for 8-bit I420, reports `0:0` SAR and 25/1 fps (E8), and counts frames from a seekable file length only. Non-I420/non-8-bit formats are rejected with an explicit I0 limitation instead of being silently mishandled. |
| `open_y4m` | Parses the header tokens W/H/F/A/I/C after the already verified magic, defaults SAR to 1:1 and rate to 25/1 when absent, and accepts the standard 4:2:0 chroma labels. Unsupported chroma is rejected by name. The demuxer info line therefore reports the source rate and SAR while `--fps`/`--sar` still override the encoder parameters. |
| `io_read`, `io_getc`, `io_unread`, `io_reset`, `io_read_line` | Implement one buffered byte source shared by probe, header parse and frame read. Push-back before the buffer guarantees that probing does not consume data on pipes as well as files; `io_read_line` strips CR so CRLF Y4M files work. Short reads are observable as truncated frames, never as silent success. |
| `io_count_frames` | Uses the file length divided by the frame size for regular files only and returns −1 (unknown) for stdin. Resetting the byte source after the seek leaves raw reading at byte 0. |
| `read_one`, `x264pp_input_read_frame` | Y4M frames are preceded by a validated `FRAME` line; raw frames have no header. A short frame read is an error; a clean zero-byte read at a frame boundary is end of stream, which is how "seek past EOF" becomes an empty, successful encode (E11). Forward seeks discard whole frames, so `--seek` works for stdin too. Plane pointers are offsets into one reusable frame buffer with the documented I420 strides. |
| `x264pp_input_close` | Frees the frame buffer and closes only owned file handles; stdin is left open. Idempotent for a NULL handle. |
| `x264pp_output_open` | Resolves `--muxer auto` from the extension, preserving the documented `.mp4` error and the raw default for unknown suffixes (E26). MKV/FLV are named but honestly rejected in I0. `-` maps to stdout; any other open failure produces the documented diagnostic. The file is opened **only after** the core gate, so the I0 stub cannot create or truncate an output file. |
| `x264pp_output_write`, `x264pp_output_close` | Write encoder bytes verbatim with no reformatting; a short write is an error. Stdout is flushed but not closed. This is the whole raw Annex B contract for I0. |
| `core/api.h` | Fixes the boundary types (parameters, picture, frame type, status codes). The CLI never depends on codec internals, so later increments can refine behind the same interface. |
| `core/api_stub.c` | Every entry point returns `X264PP_ERR_NOT_CERTIFIED`, sets no bitstream length and creates no encoder instance. `x264pp_codec_status()` supplies the exact text the CLI logs. This is the honest reason I0 produces no bitstream. |
| `src/Makefile` | Derives `SRC_DIR` from its own path, so sources are found regardless of the invocation directory; all objects and the executable go under `BUILD_DIR` (default: repository `build/`). The C rule and the (currently unused) NASM rule keep the toolchain fixed for I1..I5. `clean` removes only `BUILD_DIR`. |
| `x264pp_cli_main` | Order of checks reproduces the observable precedence: help/version before validation; output presence before input presence (no-arguments case, §2); input open before the core gate (so E6/E7 diagnostics remain observable); timebase incompatibility before any encoding. The core gate precedes output open, which is what guarantees "no bitstream yet". The post-gate loop is compiled so the CLI/output contract is fixed, but it is unreachable until I1. |

## 4. Questions and unknowns

These are recorded here rather than answered by guessing. I0 owns no
`src/verification/questions.md`; this file is the implementation-side question
log for this increment.

1. **Missing rebuild documents.** `docs/rebuild/x264.c.md`, `configure.md` and
   `Makefile.md` (and `output/raw.c.md`, `output/output.h.md`,
   `input/y4m.c.md`) are not present at the time of writing. I0 therefore
   derives its CLI directly from `spec/cli-blackbox.md` and the documents that
   do exist (`x264cli.h.md`, `input/input.h.md`, `input/input.c.md`,
   `input/raw.c.md`). Please answer/expand via `spec/` if CLI details beyond
   the black-box spec are required.
2. **Help text.** The spec fixes the `--version` block, help line counts and
   the first line of `--fullhelp`, but not the verbatim body. `print_help`
   therefore emits an original, honest option summary rather than claiming a
   435-line transcript. Line counts are **UNKNOWN** for the clean build.
3. **Progress/statistics lines.** Format is specified, but the values depend
   on an encoder; they are intentionally not fabricated in I0.
4. **Exact clamping ranges** for most integer options beyond E12/E14 are
   marked UNKNOWN in the spec. `apply_option` uses the documented nominal
   ranges and clamps silently; certification should not treat these numbers as
   a contract until the spec team confirms them.
5. **Container muxers** (MKV/FLV) and non-I420/10-bit input/output are
   explicitly rejected in I0 rather than approximated. Their CLI behaviour is
   specified but their implementation belongs to a later increment.
6. **Zero-copy/mmap input.** `docs/rebuild/input/input.c.md` describes mmap
   fast paths; I0 uses one buffered frame read instead. This is a performance
   refinement for I5, not a behavioural deviation at the CLI boundary.
7. **`--vf`, zones, qpfile, VUI, pass/stats** are accepted and stored but not
   validated/acted upon; the spec marks their deeper behaviour UNKNOWN.
8. **Automatic thread count** is resolution/CPU dependent and UNKNOWN; I0
   stores `--threads` but the core does not use it.
