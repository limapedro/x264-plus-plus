# I1 — box-structure verification argument

Status: **increment I1, implementation side**. Every claim below is a review
argument derived from `spec/h264-syntax.md`, `docs/rebuild/common/{dct,quant,predict,bitstream,macroblock}.c(.md)`,
`docs/rebuild/encoder/{cavlc,set,encoder}.c.md` and the published H.264
standard. No reference source was read; no oracle was run; no binary was
executed and no functional test was performed. The only execution was the
compile/link check recorded in §7.

## 1. Black box → state box → clear box

### 1.1 Black box (required external behaviour)

```
CLI1( args, input_bytes ) -> ( annex_b_bytes, stderr_log, exit_code )
```

For I1 the CLI/IO behaviour is the I0 contract with the honest stub replaced
by an encoder. A structurally valid invocation:

* opens the input and logs its properties (I0 behaviour, unchanged);
* allocates an encoder from the resolved parameter block;
* for every input picture, appends one access unit to the output byte stream:
  the first access unit is SPS (type 7) → PPS (type 8) → IDR slice (type 5);
  later access units contain only an IDR slice;
* emits no output file at all when the encoder cannot be created;
* exits 0 after the frame loop and flush.

The required *codec* black box is narrower:

```
CODEC1( param, picture ) -> ( annex_b_bytes, frame_type )
```

where `annex_b_bytes` must contain an active SPS/PPS and a decodable I-slice
with the picture's geometry, 8-bit 4:2:0 chroma, CAVLC entropy coding and no
inter prediction.

### 1.2 State box

```
( stimulus, old_state ) -> ( response, new_state )
```

`old_state` is the encoder instance:

| State | Where | Purpose |
| --- | --- | --- |
| resolved parameters `(width,height,fps,sar,qp,…)` | `x264pp_encoder_t.param` | fixed for the stream |
| SPS/PPS and their serialised RBSP bytes | `sps`, `pps`, `sps_rbsp`, `pps_rbsp` | emitted exactly once |
| padded source frame | `fenc` | mode decision and residual |
| padded reconstruction frame | `fdec` | neighbour samples for prediction and CAVLC context |
| per-4x4-block nonzero counts | `nz_y`, `nz_c[2]` | `nC` for the next macroblock |
| header-emitted flag, frame number | `wrote_headers`, `frame_num` | access-unit structure |
| bitstream scratch | `slice_rbsp` | one slice per picture |

The refinement keeps all of this explicit; nothing in the CLI depends on it.
The frame boundary is the state boundary: `fdec` is *not* reset between
pictures (so intra prediction inside a picture uses samples reconstructed
earlier in that picture), while every picture starts with a fresh `fdec`
filled with 128, because every picture is an independent IDR.

### 1.3 Clear box (procedural decomposition)

```
x264pp_encoder_open
  -> x264pp_params_validate
  -> x264pp_encoder_create
       -> x264pp_sps_init / x264pp_pps_init / x264pp_level_auto
       -> x264pp_frame_alloc (fenc, fdec) -> x264pp_frame_fill(fdec,128)
       -> write_sps / write_pps -> x264pp_bs_trailing

x264pp_encoder_encode
  -> x264pp_encoder_encode_frame
       -> x264pp_frame_load (copy + edge padding)
       -> [first frame] append SPS NAL, append PPS NAL
       -> write_slice_header (IDR)
       -> for each macroblock:
            gather_neighbors -> x264pp_pred16 (4 modes, SAD choice)
            x264pp_dct4 -> x264pp_hadamard4 -> x264pp_quant4
            x264pp_dequant4 -> x264pp_hadamard4_inv -> x264pp_idct4_add
            (analogous chroma path with hadamard2)
            x264pp_cavlc_residual (DC, luma AC, chroma DC, chroma AC)
       -> x264pp_bs_trailing
       -> x264pp_bs_nal (emulation prevention + Annex B start codes)

x264pp_encoder_close -> x264pp_encoder_destroy
```

## 2. Per-function verification arguments

Each row is an *intended-function* claim: assuming its callees behave as
specified, the function preserves the box above it.

| Function | Intended function and refinement argument |
| --- | --- |
| `x264pp_params_validate` | Rejects invalid geometry/colour/depth before any allocation, resolves 0 counts to the documented defaults, and forces the I1-only knobs (CAVLC, 4x4 transform, no B frames, one reference, no deblocking) to their supported values. Because the caller's CLI state is copied, later mutation cannot change the encoder mid-stream. |
| `x264pp_sps_init` | Computes `mb_width=ceil(w/16)`, `mb_height=ceil(h/16)` and the crop offsets that recover the uncropped resolution; picks Baseline (or High when requested), level by Annex A limits, POC type 0, one reference, progressive frame-only coding and direct-8x8 inference. The VUI carries timing and the minimal bitstream-restriction block, matching `spec/h264-syntax.md` §3.2/§10. |
| `x264pp_pps_init` | Selects CAVLC (`entropy_coding_mode_flag=0`), zero slice groups, neutral initial QP equal to the frame QP (so `slice_qp_delta=0`), and a deblocking-control flag so the slice can disable filtering explicitly. |
| `x264pp_level_auto` / `x264pp_level_validate` | Walk the Annex A table in increasing level order and choose the first entry satisfying frame size, macroblock rate and DPB; validation reports a nonzero code when any bound is exceeded. The level table is fixed standard data, not a heuristic. |
| `x264pp_frame_alloc/load/fill` | Allocates one contiguous buffer per frame with 16/8-sample padding on each side; copies the caller's three I420 planes row by row and replicates edges so that a predictor reading `t[x]`/`l[y]` at a picture border sees a defined sample. `fill` starts `fdec` at 128, the H.264 neutral sample value. |
| `x264pp_bs_init/write/u/ue/se/trailing/bytes` | Bit-exact MSB-first writer; `ue` writes `k` zeros, a one and a `k`-bit suffix so `codeNum = 2^k−1+suffix`; `se` uses the standard mapping `0→0, 1→1, 2→−1, 3→2, 4→−2`; `trailing` appends the stop one and alignment zeros. This is §1.1–1.2 of the syntax spec. |
| `x264pp_bs_nal` | Emits a 3- or 4-byte Annex B start code, the NAL header `(ref_idc<<5)|type` with forbidden bit zero, then copies the RBSP while inserting `0x03` whenever the last two emitted bytes were zero and the next byte is `≤3`. Working from the *destination* zero-run makes consecutive insertions impossible, matching §1.3–1.4 and the worked example in `docs/rebuild/common/bitstream.c.md` §5.4. |
| `x264pp_dct4`, `idct4_add` | Forward separable butterfly `(p+q, 2r+s, p−q, r−2s)` with no shift; inverse 1-D lanes `(u+w, v+z, v−z, u−w)` with the odd inputs halved, a final `+32>>6` and saturating add. A constant block puts all energy in DC; a DC-only inverse adds `DC>>6` to every sample, as required by H.264 8.5. |
| `x264pp_hadamard2/4` and inverses | Unnormalised Hadamard stages with the decoder's `>>1` (2x2) and `>>2` (4x4) on reconstruction. The two-stage luma DC transform places a constant block's energy in coefficient 0; the inverse recovers one DC value per 4x4 block. |
| `x264pp_quant_init/4/2`, `dequant4/2` | Applies the H.264 levelScale vector `{10,11,13,14,16,18}` with the `qp/6−4` reconstruction shift, using 64-bit intermediates and a dead-zone bias. Normal 4x4 AC blocks use the factor that makes decoder dequantisation recover four times the forward DC (the IDCT normalisation), Hadamard DC blocks use half of it. Sign is reattached after magnitude arithmetic. |
| `x264pp_predict16/4/8c/8/8_edge` | Generate the standard V/H/DC/plane and directional predictors from already-reconstructed neighbours; availability flags substitute 128 and legal-mode fix-up maps unsupported modes to DC. The 8x8 edge filter applies the specified three-tap smoothing to left/top neighbours before directional modes. |
| `x264pp_cavlc_residual` | Counts trailing ±1 levels (max three), writes `coeff_token` selected by `nC`, trailing signs, adaptive-suffix level prefixes, `total_zeros` and `run_before` in the normative order; all-zero blocks emit the single `coeff_token(0,0)` code. This implements §7.1 of the syntax spec. |
| `x264pp_cavlc_cbp_code` | Maps the combined chroma/luma CBP to the intra codeNum used by `I_4x4` macroblocks; retained for the later increment that enables `I_4x4`. |
| `encode_mb` | Chooses the 16x16 prediction mode by minimum SAD, forms and quantises luma/chroma residuals, reconstructs into `fdec`, then writes `mb_type`, `intra_chroma_pred_mode`, `mb_qp_delta`, luma DC, luma AC (when CBP), chroma DC and chroma AC (when CBP=2) in syntax order. Neighbour nonzero counts are stored for the next macroblock's `nC`. |
| `write_slice_header` | Writes the I-slice header in normative order with `slice_type=7`, `frame_num=0` for IDR, `idr_pic_id=0`, `pic_order_cnt_lsb=0`, IDR marking flags, zero QP delta and `disable_deblocking_filter_idc=1`. This is §5 of the syntax spec. |
| `x264pp_encoder_encode_frame` | Loads the picture, emits SPS/PPS on the first access unit, writes one IDR slice, appends trailing bits and encapsulates each NAL with emulation prevention. Bounds are checked at every append, so a too-small output buffer fails rather than overruns. |
| `api.c` entry points | Validate parameters, translate the CLI's opaque handle into the concrete encoder, treat `pic==NULL` as a flush with no delayed frames, and release all owned memory. The I0 stub is deleted; the CLI source is untouched. |

## 4. Deferrals and unknowns

Explicitly not implemented in I1 (see `questions.md` for the full list):

1. **Deblocking filter is disabled** by `disable_deblocking_filter_idc=1`. No
   filter is modelled in reconstruction. This is a documented deviation from
   the I1 exit-criterion wording and is the first item to revisit.
2. **Macroblock types limited to `I_16x16`.** `I_4x4`, `I_8x8`, `I_PCM`, the
   `me(v)` CBP mapping and `transform_size_8x8_flag` are not emitted; the
   predictor library nevertheless implements all intra modes.
3. **CABAC, P/B slices, motion estimation, reference management** are absent by
   scope, as required by the increment statement.
4. **CAVLC VLC bit patterns** are transcribed from the published H.264 tables;
   their exactness must be confirmed by an independent decoder.
5. **Quantisation factors** (4 for 4x4 AC, 2 for Hadamard DC) were derived from
   decoder normalisation rather than observed bitstreams.
6. **No SEI, AUD, filler NALs, repeat headers, end-of-sequence**; SPS/PPS are
   emitted once, on the first picture.
7. **Rate control is a constant-QP approximation**: `--crf C` maps to QP≈C and
   `--qp Q` maps to Q directly; no lookahead, MB-tree, AQ or VBV.
8. **High profile** SPS/PPS extensions are written when requested, but High
   profile is not selected by default and the 8x8 transform is never used.
9. **Output buffer** capacity is externally bounded (`w*h*6+4096` from the
   CLI); `append_nal` fails safely if a NAL does not fit.

## 8. Bitstream-validity verification (fix/bitstream-validity)

An independent decoder check was performed with the locally installed ffmpeg:

```
ffmpeg -hide_banner -v error -i cand.264 -f null -
```

Before this change the command reported `corrupted macroblock 0 0
(total_coeff=-1)` on any textured input; flat/constant inputs decoded cleanly.
The following conformance defects in the CAVLC path were confirmed against the
published ITU-T H.264 tables (clause 9.2) and corrected:

* `x264pp_cavlc_residual` emitted a level code for every scan position below
  the last non-zero coefficient, including zero positions; zeros are described
  by `total_zeros`/`run_before` instead.
* `coeff_token_category` mapped neighbour counts `nC=5` and `nC=6` to the
  chroma-DC tables; they are ordinary neighbour counts and must use the
  `4<=nC<8` table. Chroma DC now passes the dedicated contexts `-1`/`-2`.
* Intra16x16 luma AC and chroma 4x4 AC blocks were written as 16-element
  arrays; H.264 codes only the 15 AC levels (the DC level is separate).
* The two chroma DC blocks were written interleaved with their AC blocks;
  clause 7.3.5.3 requires both DC blocks first, then all AC blocks.
* The Intra16x16 DC block's `nC` was hard-coded to 0 instead of being derived
  from the neighbours of luma block 0 (clause 9.2.1).

Those fixes are retained in the CAVLC writer, and `encode_mb` still contains
the full prediction / transform / quant / reconstruction / CAVLC syntax path.
However the I_16x16 residual subsystem could not be made bitstream-conformant
for textured content in this increment: independent decoding with ffmpeg still
reports `total_coeff=-1`, `Invalid level prefix` or `negative number of zero
coeffs` for macroblocks with luma AC residuals, even after matching ffmpeg's
exact `pred_non_zero_count` rule.  Therefore `encode_mb` currently selects the
I_PCM fallback (H.264 Table 7-11 `mb_type = 25`) for every macroblock.  This is
a correctness-first choice that trades compression ratio for the required
zero-error decode guarantee, and remains open work.

Verification results (all with `ffmpeg -v error -i ... -f null -`, no output):

* 16x16 and 64x64 synthetic clips (flat, constant, checkerboard, random noise,
  smooth gradients, `testsrc2`) — zero errors.
* Real content: `D:\Videos\Wx264-reference\fortnite_prefix128.yuv` at
  1920x1080, 8 frames — zero errors (25,287,468 bytes emitted).

Build: `make -f src/Makefile` with MSYS2 MinGW-w64 GCC 16, no warnings.


## 9. I_16x16 CAVLC implementation status (feat/i16-cavlc)

The black-box/state-box/clear-box argument above remains the design intent.
The implemented active path now emits `I_16x16` (Table 7-11) instead of
`I_PCM`; the I_NxN `rem_intra4x4_pred_mode` divergence is bypassed.  Measured
results with the exact commands in `cavlc-progress.md`:

| Check | Result |
| --- | --- |
| `make -f src/Makefile` | clean, no warnings |
| ffmpeg decode, 64x64 testsrc2, 8 frames | exit 0, empty stderr |
| ffmpeg decode, 1920x1080 fortnite, 8 frames | exit 0, empty stderr |
| ffprobe geometry | 1920x1080 yuv420p |
| 8x1080p size | 314,677 bytes (limit 400,000) |
| PSNR vs raw source, matched 25 fps | 12.71 dB (limit 25, oracle 42.64) |

Quality acceptance is therefore **not met**; the known-good I_PCM fallback is
kept behind `X264PP_FORCE_PCM`.  The residual defect is localised to the
second-stage Intra16x16 luma DC Hadamard reconstruction, not to CAVLC or to
the 4x4 AC path.


## 10. DC-ordering follow-up (same PR)

The Intra16x16 DC stage now uses the measured H.264 8.5.10 Hadamard sign
matrix (`dc_sign`) and a decoder-calibrated 4x DC scale; luma/chroma AC use
decoder-measured per-frequency scales.  Re-measured acceptance:

| Check | Result |
| --- | --- |
| build | clean |
| ffmpeg decode 64x64 / 8 frames | exit 0, empty stderr |
| ffmpeg decode 1920x1080 / 8 frames | exit 0, empty stderr |

| 16x16 DC probe | 64/129/192/64 at QP23; 65/135/191/65 at QP45 |

The DC probe ordering defect is fixed; the quality target is not met at a
size-compliant QP.  I_PCM remains the known-good quality fallback.


## 11. Default-path decision (final state)

`X264PP_FORCE_PCM` defaults to 1, so the shipped binary uses the known-good
all-I_PCM path.  The I_16x16 CAVLC path is opt-in with
`-DX264PP_FORCE_PCM=0`.

| Path | ultrafast | medium | veryslow | PSNR (8x1080p) |
| --- | --- | --- | --- | --- |
| all-I_PCM (default) | 0.99x | 3.89x | 10.64x | lossless |
| I_16x16 CAVLC | 0.41x | 1.60x | 4.23x | 12.96 dB (oracle 42.64) |
