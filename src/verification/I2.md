# I2 — genuine inter prediction: P slices with one reference

Status: **increment I2, implementation side; inter path compile-time gated**.
All claims are derived from `spec/h264-syntax.md`,
`docs/rebuild/encoder/{me,macroblock,analyse,ratecontrol,set}.c.md`,
`docs/rebuild/common/mc.c.md` and the published ITU-T H.264 standard. No
reference source was read, no oracle binary was run. ffmpeg 8.1.2 was the
authoritative decoder for every validity claim below.

## 0. Gating decision (follow-up to PR #26)

`X264PP_INTER_P` now controls whether P slices are emitted at all:

| Build | `-DX264PP_INTER_P` | Behaviour |
| --- | --- | --- |
| default (`make -f src/Makefile`) | **0** | Known-good I1 all-IDR stream, bit-identical to the pre-P baseline; certified speed preserved |
| inter (`CPPFLAGS=-DX264PP_INTER_P=1`) | **1** | Full I2 P-slice implementation retained for further tuning |

The gate is defined in `src/core/encode.h` and covers the encoder struct
(`ref`, `mv_cache`, `inter_mbs`), all inter helpers, the P slice header/data
branches, reference snapshot, `frame_num` advance, API frame-type reporting
and the human-readable codec status string. With the macro off the extra
state is not even allocated, so the default build has no ME or MC overhead.

Reason: the integrating session measured a certified-speed regression with
P slices enabled (1080p: **0.53x ultrafast / 2.01x medium / 6.01x veryslow**,
versus **1.01x / 3.93x / 11.00x** for the current default). The exhaustive
+/-8 full-pel SAD search is the dominant cost, so the faster all-IDR path
remains the default until ME is optimised. The same session reported an
inter-enabled stream decoded cleanly by ffmpeg at 1920x1080, 8 frames,
**size ratio 0.94 vs oracle** and **PSNR 27.08 dB**; those numbers are
reproduced verbatim here as *reported* figures (§2.4). Locally reproducible
figures for the gated build are given separately so nothing is conflated.

## 1. Black box → state box → clear box

### 1.1 Black box

```
CODEC2( param, picture[0..N-1] ) -> annex_b_bytes
```

* Picture 0 is always an **IDR** access unit. With the default build it is
  byte-for-byte the certified I1 all-I_PCM IDR; with
  `-DX264PP_FORCE_PCM=0` it is the I_16x16 CAVLC IDR.
* With `X264PP_INTER_P=0` (default), pictures 1..N-1 are further IDR slices:
  the complete I1 stream, unchanged.
* With `X264PP_INTER_P=1`, pictures 1..N-1 are **non-IDR P slices**
  (`NAL type 1`, `nal_ref_idc=3`, `slice_type=5`) with exactly one active L0
  reference: the immediately preceding reconstructed picture.
* Every P macroblock is either `P_Skip` (inferred type, no macroblock syntax)
  or `P_L0_16x16` (`mb_type=0`) with full-pel `mvd_l0`, CBP via `me(v)`,
  `mb_qp_delta` and CAVLC residual, in normative order.

### 1.2 State box

`x264pp_encoder_t` gains three pieces of state over I1:

| State | Purpose |
| --- | --- |
| `ref` | padded copy of the previous reconstructed picture; the single L0 reference |
| `mv_cache[mb_count][2]` | per-MB MVs, in quarter-luma units, for H.264 8.4.1.2.1 median prediction |
| `inter_mbs[mb_count]` | per-MB decision (skip, MV/MVP, CBP, levels) so `mb_skip_run` can be written in one pass |

`frame_num` advances for every picture. `nz_y` / `nz_c` are picture-local
CAVLC neighbour-count caches and are cleared at the start of each picture.
Frame 0 has no reference; `ref` is initialised to neutral 128.

### 1.3 Clear box

```
x264pp_encoder_encode_frame
  -> frame_load
  -> [first AU] append SPS, PPS
  -> write_slice_header( IDR | P )
  -> is_idr ? encode_mb()                     (unchanged I1 path)
            : write_inter_slice_data()
                -> for each MB: predict_mv -> SAD search (+/-8, full pel)
                              -> mc_inter_block -> DCT/quant -> CAVLC levels
                -> for each MB: mb_skip_run / P_Skip | P_L0_16x16 syntax
  -> rbsp trailing, emulation prevention, Annex B
  -> copy_ref_frame (fdec -> ref, picture-edge extension)
  -> frame_num++
```

With `X264PP_INTER_P=0` the `write_inter_slice_data` branch, `copy_ref_frame`
and the `frame_num++` step are compiled out entirely: every picture follows
only the `encode_mb()` IDR path.

`predict_mv` uses the component-wise median of A (left), B (above) and
C (above-right, or D above-left when C is unavailable); unavailable and
intra neighbours contribute (0,0). Motion compensation is a full-pel luma
copy plus the 8.4.3 chroma bilinear rule; all MVs are multiples of four
quarter-luma units. The search prefers the zero vector on ties, which makes
static macroblocks collapse to `P_Skip`.

## 2. Acceptance evidence (exact commands and outputs)

Environment: MSYS2 MinGW-w64 GCC 16.2.0, GNU Make 4.4.1, NASM 2.16.03,
ffmpeg 8.1.2, Python 3.14.7. All commands run from `E:\_wt\x264pp-inter`.

### 2.1 Default build: bit-identical pre-P baseline

```
make -f src/Makefile clean
make -f src/Makefile
```
→ clean, no warnings, no errors.

```
ffmpeg -y -f lavfi -i 'testsrc2=size=64x64:rate=30' -frames:v 8 \
  -pix_fmt yuv420p -f rawvideo tiny.yuv
build/x264pp.exe --demuxer raw --input-csp i420 --input-res 64x64 --fps 30 \
  --preset medium --threads 1 --frames 1 --no-progress -o one.264 tiny.yuv
build/x264pp.exe --demuxer raw --input-csp i420 --input-res 64x64 --fps 30 \
  --preset medium --threads 1 --frames 8 --no-progress -o baseline.264 tiny.yuv
Get-FileHash one.264 -Algorithm SHA256
Get-FileHash baseline.264 -Algorithm SHA256
ffmpeg -hide_banner -v error -i baseline.264 -f null -
```

| Output | SHA256 |
| --- | --- |
| 1 frame | `3C8DEBB00D6207EC09299AF4541D34E6ACEE6943578E1DE0AA9089BF0E61C84D` |
| 8 frames | `83C71EBCC7A01E991F052CDDFC8BFE8E7B4BA27DC7A498A103DC7EE8C00F0DB1` |

Both hashes match the pre-P I1 baseline exactly (the 8-frame value is the

### 2.2 Inter-enabled build

```
make -f src/Makefile BUILD_DIR=build-inter CPPFLAGS=-DX264PP_INTER_P=1
build-inter/x264pp.exe --demuxer raw --input-csp i420 --input-res 64x64 \
  --fps 30 --preset medium --threads 1 --frames 8 --no-progress \
  -o tiny-inter.264 tiny.yuv

```
→ exit 0, empty stderr; SHA256
`ECFCFF011F180AE39B328B8BC815314EE02C2B63776357929BEB8F50C1F1E80D`
(differs from the all-IDR baseline, as expected).

```
build-inter/x264pp.exe --demuxer raw --input-csp i420 --input-res 1920x1080 \
  --fps 25 --preset medium --threads 1 --frames 8 --qp 45 --no-progress \
  -o fort-inter.264 D:\Videos\Wx264-reference\fortnite_prefix128.yuv
ffmpeg -hide_banner -v error -i fort-inter.264 -f null -
ffprobe -v error -count_frames -select_streams v:0 \

```
→ ffmpeg exit 0, empty stderr; `width=1920`, `height=1080`,
`nb_read_frames=8`; output **3,267,400 B**. Locally measured PSNR vs raw
source: **26.90 dB** (Y 25.29 / U 35.71 / V 37.93), with lossless I_PCM
frame 0 dominating the file size.

For an apples-to-apples baseline comparison, the I_16x16 frame-0 variant
with the inter gate on was also built:

```
make -f src/Makefile BUILD_DIR=build-inter-gate \
  CPPFLAGS="-DX264PP_INTER_P=1 -DX264PP_FORCE_PCM=0"
build-inter-gate/x264pp.exe ... --crf 23 -o fort-inter-gate.264 ...
```
→ ffmpeg exit 0, empty stderr; **172,178 B**, PSNR **21.90 dB**
(Y 20.70 / U 26.02 / V 26.64) — 41 % smaller than the 293,151 B
I-frame baseline, with the quality regression explained in §4.

The integrating session reported a verified inter-enabled 8-frame

### 2.4 `cert/bitstream_diag.py`

```
python cert/bitstream_diag.py fort-inter.264 > diag.txt
```
→ exit 0, `SUMMARY: NALs=10 SPS=1 PPS=1 macroblocks=8160 errors=0`.
Note the diagnostic intentionally stops its macroblock-layer decoder at P
slices ("only I-slice macroblock layer is decoded"), so its zero-error
result is necessary but not sufficient; ffmpeg is authoritative.

### 2.5 P_Skip / P_L0 coverage

A 3-frame constant-colour clip produces all-skip P slices (output 6,280 B,
ffmpeg clean). A forced all-coded variant (`--qp 23`, textured content)
exercises `mb_type=0`, `mvd_l0`, `me(v)` CBP and CAVLC chroma residual;
a scratch bit reader that implements the normative CAVLC tables and a
proper per-picture `non_zero_count` cache parses all seven P slices with
zero residual errors. That reader is a temporary analysis tool in the
approved temp directory, not part of the repository.

## 3. Per-function verification argument

| Function | Intended function |
| --- | --- |
| `write_slice_header` | IDR branch is the untouched I1 byte sequence; P branch writes `slice_type=5`, `frame_num`, even POC lsb, `num_ref_idx_active_override_flag=0`, `ref_pic_list_modification_flag_l0=0`, `adaptive_ref_pic_marking_mode_flag=0`, then the common QP/deblocking tail. |
| `predict_mv` | H.264 8.4.1.2.1 median of A/B/C(D) in quarter-luma units; (0,0) for unavailable or intra neighbours. |
| `analyse_mb_inter` | +/-8 full-pel SAD search with (0,0) tie preference; MC into `fdec`; luma/chroma DCT+quant reconstruct; chooses P_Skip only when MV==MVP and the residual is empty. |
| `write_mb_inter` | `P_L0_16x16` syntax: `mb_type=0`, `mvd_l0` (no `ref_idx_l0` with one active ref), `me(v)` CBP via Table 9-4, `mb_qp_delta`, CAVLC luma/chroma residual; updates the NNZ caches in scan8 order. |
| `write_inter_slice_data` | Two-pass analyse/then-write lets it emit correct `mb_skip_run` counts, including the trailing run. |
| `copy_ref_frame` | Copies the coded picture and extends every edge from the *picture* edge (important at 1080p, where the coded height is 1088). |
| `api.c` | With `X264PP_INTER_P=1`, reports `X264PP_FRAME_P` for pictures after the IDR; with the gate off, always reports IDR. Flush and lifetime behaviour unchanged; the status string follows the gate. |

## 4. Honest limitations and open work

1. **Certified speed is the reason P slices are off by default.** The
   integrating session measured 0.53x / 2.01x / 6.01x (ultrafast / medium /
   veryslow) at 1080p with P slices, against 1.01x / 3.93x / 11.00x for the
   all-IDR default. `X264PP_INTER_P=0` restores the certified path
   byte-for-byte; enabling the gate is an explicit opt-in for tuning.
2. **Luma residual is disabled in the shipped build** (`X264PP_INTER_LUMA_RESIDUAL=0`).
   With it enabled, the emitted luma CAVLC is self-consistent under an
   independent Table-9-5 reader but ffmpeg rejects dense luma-residual
   blocks, e.g. `mb_type 26 in P slice too large at 2 2`,
   `mb_skip_run 75 is invalid`, `cbp too large (90) at 1 3` on 64x64
   `testsrc2` at QP23 and on the 1080p clip at QP45. Reducing the residual
   (QP45 on 64x64, flat or static content) makes the same encoder
   ffmpeg-clean, so the defect is in the high-density CAVLC path shared with
   the I1 gated I_16x16 mode (that mode also fails at QP23 on the same clip:
   `run_before=12 > zerosLeft=8`, `cert/bitstream_diag.py` exit 1). It was
   not fixed here because `cavlc.c` is outside this increment's ownership.
   The macro `X264PP_INTER_LUMA_RESIDUAL=1` restores the experimental path
   for diagnosis; it is **not** the shipped build.
   Consequence: luma samples of P frames are motion-compensated copies;
   chroma residual, MV coding and P_Skip remain fully coded. In the gated
   build this lowers PSNR from the 26.24 dB I-frame baseline to 21.90 dB;
   in the default build the lossless IDR keeps PSNR at 26.90 dB.
3. **Single reference, full pel only.** No sub-pel interpolation, weighted
   prediction, multiple references, B frames or deblocking modelling
   (`disable_deblocking_filter_idc=1`, as in I1).
4. **Search** is an exhaustive +/-8 luma SAD with (0,0) tie preference; there
   is no SATD/RD, MVP-biased cost, early termination or chroma ME.
5. **Rate control** is unchanged: constant QP from `--qp`/`--crf`.
6. `cert/bitstream_diag.py` does not decode P-slice macroblocks, so its
   P-slice result is only a header/SPS/PPS check.
7. **Parallel CLI path.** The CLI's threaded path opens one encoder per
   worker, so each worker sees only its own frames and starts with an IDR.
   All evidence above therefore uses `--threads 1` (the sequential path).
   Frame-level threading across a shared encoder is not implemented.

## 5. Wall and test discipline

* Only `spec/`, `docs/rebuild/`, `src/` and `cert/` were read. The dirty
  reference tree, `oracle/` binaries and any reference encoder source were
  never accessed. Temporary harnesses and test media live under
  `C:\Users\multi\AppData\Local\Temp\opencode\`.
* No line of reference source was copied; all new code is original and
  written from the published standard and the behavioural specifications.
* The binary was executed extensively with our own inputs; ffmpeg results
  above are literal observations, not projections.

## Luma-residual recheck (2026-11-28)

With current CAVLC fixes, `-DX264PP_INTER_LUMA_RESIDUAL=1` at QP45 produces byte-identical output to the shipped QP45 path (all luma levels quantise to zero; 3,265,957 B, ffmpeg clean). At QP23 it still desyncs: 3,623,246 B vs 3,317,469 B with residual off, and ffmpeg reports `top block unavailable for requested intra mode` from MB 56 0. The dense-luma CAVLC neighbour-context issue therefore remains unresolved; the experimental macro stays off. No patch merged.
